P-256 等 NIST 椭圆曲线是今天 HTTPS、手机安全芯片和 Passkey 都在用的加密标准，但它的「种子」由美国国家安全局（NSA）在 1990 年代提供、从未解释来源，所以 25 年来一直有人怀疑里面藏了后门。据 Anthropic 10 月 16 日的文章，一位员工在没给任何提示的情况下让内部研究模型试试，Claude 不到半小时就换了个角度破了案：它去推测 90 年代生成曲线的软件是怎么写的，最终证明种子只是用时间戳初始化的普通随机数。这反而让「故意埋后门」的说法更站不住，Anthropic 也强调这不是破解，加密本身没有新漏洞。

核心要点

  • 悬案来历：2000 年 NIST 把 ECDSA 写进标准；流传最广的说法是 NSA 的 Jerry Solinas 称种子是一句玩笑话的哈希（比如「Give Bob and Jerry a raise」），他 2023 年去世后线索中断，Anthropic 内部好几个人沿这条线找过都没找到。

Google 开源 Harness²：让 Agent 自己改 Prompt/Skill/Memory，反复试出更好配置↗

做 Agent 的人大部分时间其实不是在换模型，而是在反复调模型外面那一层配置——提示词、工具说明、记忆、Skill 等，业内叫 harness。Google Research 开源的 Harness² 想把这件苦差事交给 Agent 自己：针对一个具体任务，它自己尝试几种改法、实际跑一遍比较效果，再把有效的改动合并起来，并把经验留给以后类似的任务。Xudong 前几天解读过它的论文，这次推荐的是刚放出的代码，同一天还有好几位博主在介绍它。论文里的提升不小，但他提醒试错要花的额外成本、经验能否用到新任务上，都还要再看。

核心要点

  • 它改的是哪一层：harness 指包在模型外面的系统提示词、护栏、记忆、工具说明、子 Agent、Skill、脚本和插件八类组件；Harness² 不训练模型、不改权重。

论文：约 16 个 memory token 打赢全上下文，源文档用量少约 108 倍↗

elvis @omarsar032.5万 粉丝10月19日 01:59长帖

推荐原因做 Agent 长期记忆时，可当「压缩表征 vs 塞全文」的硬对照。

想让 AI Agent 记住大量资料，现在主要有两种办法：把全文都塞进上下文，或者用检索把相关段落找回来，两种都很耗 token，资料一多就撑不住。Omar（DAIR.AI）介绍了一篇换了思路的论文：资料只处理一次，存成模型能直接读懂的压缩形式，每次提问时只取出一小撮浓缩后的信息交给模型，而且模型本身不用重新训练。实验里它在用量少得多的情况下，比塞全文还答得准，拿来当 Agent 的「经历记忆」也有效。Omar 认为这是让模型在长期使用中不断积累知识的一条可行路线。

核心要点

  • 方法名叫 Latent Semantic Memory（潜在语义记忆）：文档预先编码成向量存起来；提问时，一个训练过的小模块从整个资料库中挑出相关内容，压缩成 16 个「记忆 token」，再交给权重冻结（不改动）的大模型。
  • 关键数据：在事实核查测试 FactKG 上准确率 84.33%，高于塞全文的 80.43%，而源文档占用的 token 少约 108 倍；8 个基准里有 5 个胜过 Mem0、MemoRAG 等现有记忆方案。
  • 当 Agent 记忆的效果：在文字冒险游戏 TextWorld 里，把 Agent 自己走过的历史当资料库，任务成功率从 18.6% 升到 24.2%，重复走回已去过房间的情况也变少了。
  • 和 RAG（检索增强）的区别：RAG 取回的是原文段落，仍要按原文长度占上下文；这里取回的是压缩后的表示，长度固定为 16 个 token，资料再多也不会变长。

评论总结

  • 疑问Rozov_Artem 认为 108 倍省 token 是标题，真正的问题是更新成本：源文档一改，是要把整个记忆重新编码，还是能局部修补？这决定了它能不能用在每次会话都在变的 Agent 记忆上。
  • 分歧fuzzystripe 提醒格式变了：记忆从文字变成 16 个只有特定模型读得懂的 token，换模型或导出时就只剩一堆数字，「把记忆带走」会变得很难。
  • 亮点iPuneetSingh 和 Cyphrexio 建议先拿自己已知答案的问题测一遍：压得这么狠的记忆会悄悄丢掉个别关键事实，而且你不知道丢的是哪一条。

论文提醒：Agent 最危险的时刻，往往是它停下来让你点「确认」↗

Xudong Han @Xudong074529101.4万 粉丝10月18日 12:01长帖

推荐原因如果你在设计 Agent 产品的人工确认环节，这篇能帮你避开「有确认就安全」的错觉，把确认点设计得少而有用。

很多 Agent 产品把「关键操作前让人点确认」当成安全保障。Xudong 推荐的论文《AI Agents Push Humans Out of the Loop》（Margaret Mitchell 等人）指出，这个时刻反而可能最危险：Agent 跑了很久之后，人早已跟不上它前面做了什么，确认变成了走形式。长期依赖自动化，人自己的专业能力和接管能力也会慢慢退化。Xudong 的体会是，「人在环路」要解决的不是流程里有没有人，而是关键时刻这个人还懂不懂系统在做什么——人不是最后一道按钮，而要始终保留接管系统的能力。

核心要点

  • 「审批疲劳」（approval fatigue）的成因：几十步工具调用、状态变化和连续审批之后，每一次确认的信息量越来越低，人习惯性点「同意」，真正的判断已经掉线。
  • 论文给的改法：砍掉没意义的审批，把人的注意力留给真正高风险的节点；同时提供状态恢复（让人快速看懂现在到哪一步）、明确的权限边界和批量审查。
  • 评论里的具体设计：确认界面要直接写清这次要改什么、依据是什么、还有哪些没核实、拒绝会怎样；比如退款前把金额和客户名放在按钮正上方，其余细节留在日志里。
  • 另一种思路：让 Agent 不中断地跑，中途持续输出它对需求的理解，人只负责同意、否决或修改这些判断依据——相当于把人在环路异步化。

  • 共识tuge114514 一针见血：任务跑了两小时停下来问人，人除了点同意还能干什么？出了事这单还算他批的——确认按钮变成了背锅按钮。

Ben Horowitz 和 Gavin Baker 吵 AI 是不是泡沫：一个说借钱囤算力的「中间商」最危险，一个说 GPU 全在满负荷干活↗

推荐原因把「AI 泡沫」争论里两派各自盯的指标讲清楚了；以后看算力公司或 AI 基建股的消息，可以直接用「债务是不是刚性、单价降得多快」判断谁最危险。

这条把三位投资人关于 AI 算力的说法放在一起看。a16z 的 Ben Horowitz 回忆了互联网泡沫时期自己创办 Loudcloud 的教训：带宽最贵、最缺的时候签下高价长约，两年后价格崩盘，借钱囤带宽的公司全被拖垮。AYi 把这段历史套到今天：AI 模型的调用价格一直在降，但显卡、机房和电力还在涨价，借钱买卡再出租算力的公司两头受挤，所谓短缺是暂时的。另一位基金经理 Gavin Baker 持反方意见，认为今天的算力是真被用满了，和当年不能类比。这能帮你判断「算力泡沫」类新闻到底在争什么。

核心要点

  • Loudcloud 的数字：1999 年带宽每兆位约 1500 美元、有钱还买不到，他们被迫签了三年长约；仅两年后跌到约 50 美元，但合同还得按原价付。
  • AYi 总结的风险机制叫「刚性负债配浮动收入」：借钱买卡的利息、机房长约的租金是固定的，而出租算力的价格随市场浮动；一旦新芯片或新算法让同样的活需要更少算力，租金下跌，现金流先断。
  • Baker 的反方论据是利用率：2000 年泡沫顶峰时约 97% 的光纤埋在地下没用过，而今天几乎找不到闲置的顶级 GPU，需求是真实的。
  • Horowitz 引用 Databricks CEO Ali Ghodsi 的「快速起飞」四条件：新模型所需 GPU 远少于上一代、训练更快、更准，且这三点不断重复；他认为目前一条都没达到，所以算力需求短期不会突然塌掉。
  • 读新闻时可看三件事：公司背了多少债和长约、算力单价降得多快、用量涨得是否比单价降得快。
