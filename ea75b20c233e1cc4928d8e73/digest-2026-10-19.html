Google 开源 Harness²：让 Agent 自己改提示词、工具、记忆这层配置，不动模型权重↗

AIGCLINK @aigclink3.8万 粉丝10月18日 19:58长帖

赞 84转 0评 20阅 8,541

推荐原因如果你花很多时间调 Agent 的提示词和工具配置，这是一个可以试着把调参自动化的开源方案；上线前记得锁死护栏和留痕回滚。

做 Agent 的人大部分时间不是在换模型，而是在反复调模型外面那一层配置——提示词、工具说明、记忆、Skill 等，业内叫 harness。AIGCLINK 介绍了 Google 新开源的 Harness²：它想把这种人工试错交给 Agent 自己，面对一个新任务时先尝试几种改法、实际跑一遍比较效果，再把有效的改动合起来，任务结束后还把有证据支持的经验存下来给以后用。全程不训练模型、不改权重。Akshay、ai_for_success 等人同一天也在介绍它；评论区最关心的是它会不会把安全护栏也一起「优化」掉。

核心要点

  • 它改的是哪一层：系统提示词、护栏（Guardrails）、记忆、工具说明、子 Agent、Skill、脚本、插件八类组件；兼容 OpenCode、Codex 作为执行器，支持并行和顺序两种方式。
  • 第一层「任务级递归」是 Propose–Probe–Compose 循环：Propose 提出多个改法，Probe 让各个配置实际执行同一个任务、观察行为差异，Compose 对比执行轨迹、合成更适合这个任务的新配置。
  • 第二层「Harness 级递归」：任务完成后不只存结果，还保留采用的配置和有执行证据支持的改进经验，下次遇到类似任务先参考，相当于把调参经验自动积累起来。
  • 效果与未知数：论文在 WorkBuddy-Bench 上单轮优化最高提升 11.5 分；Xudong 提醒，反复试错多花的 token 成本、经验换到新任务上还管不管用，都还没充分验证。

论文：约 16 个 memory token 打赢全上下文，源文档用量少约 108 倍↗

elvis @omarsar032.5万 粉丝10月19日 01:59长帖

赞 123转 0评 37阅 8,001

推荐原因做 Agent 长期记忆时，可当「压缩表征 vs 塞全文」的硬对照。

想让 AI Agent 记住大量资料，现在主要有两种办法：把全文都塞进上下文，或者用检索把相关段落找回来，两种都很耗 token，资料一多就撑不住。Omar（DAIR.AI）介绍了一篇换了思路的论文：资料只处理一次，存成模型能直接读懂的压缩形式，每次提问时只取出一小撮浓缩后的信息交给模型，而且模型本身不用重新训练。实验里它在用量少得多的情况下，比塞全文还答得准，拿来当 Agent 的「经历记忆」也有效。Omar 认为这是让模型在长期使用中不断积累知识的一条可行路线。

核心要点

  • 方法名叫 Latent Semantic Memory（潜在语义记忆）：文档预先编码成向量存起来；提问时，一个训练过的小模块从整个资料库中挑出相关内容，压缩成 16 个「记忆 token」，再交给权重冻结（不改动）的大模型。
  • 关键数据：在事实核查测试 FactKG 上准确率 84.33%，高于塞全文的 80.43%，而源文档占用的 token 少约 108 倍；8 个基准里有 5 个胜过 Mem0、MemoRAG 等现有记忆方案。
  • 当 Agent 记忆的效果：在文字冒险游戏 TextWorld 里，把 Agent 自己走过的历史当资料库，任务成功率从 18.6% 升到 24.2%，重复走回已去过房间的情况也变少了。
  • 和 RAG（检索增强）的区别：RAG 取回的是原文段落，仍要按原文长度占上下文；这里取回的是压缩后的表示，长度固定为 16 个 token，资料再多也不会变长。

评论总结

  • 疑问Rozov_Artem 认为 108 倍省 token 是标题，真正的问题是更新成本：源文档一改，是要把整个记忆重新编码，还是能局部修补？这决定了它能不能用在每次会话都在变的 Agent 记忆上。
  • 分歧fuzzystripe 提醒格式变了：记忆从文字变成 16 个只有特定模型读得懂的 token，换模型或导出时就只剩一堆数字，「把记忆带走」会变得很难。
  • 亮点iPuneetSingh 和 Cyphrexio 建议先拿自己已知答案的问题测一遍：压得这么狠的记忆会悄悄丢掉个别关键事实，而且你不知道丢的是哪一条。

图解 LLM 连续批处理：为什么静态 batch 会空转 GPU，动态换人才能吃满吞吐↗

Avi Chawla @_avichawla7.9万 粉丝10月18日 18:46教程

赞 309转 0评 27阅 1.9万

推荐原因推理服务和面试都会问到的概念，图解比纯文字好记，写 Agent 或部署接口前值得过一遍。

_avichawla 用图解讲清大模型推理里的连续批处理（continuous batching）。传统机器学习一次前向里，一个 batch 的每行同时开始也同时结束；大模型解码却是每次前向只给每条序列吐一个 token，谁先遇到结束符谁先结束。如果用静态批处理，短请求结束了还要占着槽位等最长的那条跑完，GPU 大量空转。连续批处理允许请求随时进、随时出，空出来的槽立刻接下一条，这是推理服务面试和工程里提高吞吐的核心概念。

核心要点

  • 静态批处理在开跑时就固定成员：三十个 token 就结束的请求，也要等到同批四百 token 的慢请求结束才释放槽位。
  • 连续批处理把「batch 成员」改成可动态替换：有人结束就立刻换上队列里的下一条，前向仍可合并算。
  • 这对服务端吞吐影响很大，因为真实流量里输出长度差异极大，静态批会把大量算力浪费在 padding 和等待上。
  • 帖子明确写成面试常考题并建议收藏，图解适合当速查，而不是只丢一句「用 vLLM」就完事。
  • 和 PagedAttention、vLLM 等工程名词常一起出现：连续批处理解决调度，分页注意力解决显存碎片。

评论总结

  • 共识连续批处理图解被当成面试与推理服务速查收藏，静态批会空转这一点几乎无争议。
  • 亮点有人把它和分页注意力、推理引擎调度放在一起记，说终于能向同事讲清为什么要动态换人。
  • 疑问也有人追问生产里优先级与抢占怎么配，原图解偏概念，运维细节仍要对照具体引擎文档。

Ben Horowitz 团队实测：顶级模型写的网站一捅就漏，厂商却说「提示词写错了」↗

AYi @AYi_AInotes7.4万 粉丝10月18日 21:51长帖

赞 29转 0评 13阅 2万

推荐原因让 Agent 碰真数据前，用这条检查你的权限与熔断设计。

AYi 转述了 a16z 联合创始人 Ben Horowitz 在访谈里讲的一次内部测试：他们用顶级闭源模型的 Agent 写了一个网站，再让另一个 Agent 去攻击，结果轻松把客户数据全拿走；把问题反馈给模型厂商，对方的回答是「你们提示词写错了」。AYi 认为这暴露了行业的盲区：所谓安全对齐大多只是教模型说得体的话，一旦 Agent 能调用工具、读写数据库，靠提示词防风险等于裸奔；而厂商把工程缺陷说成用户的提示词问题，责任最后落到签字上线的人身上。他据此给出三条落地建议。

核心要点

  • 测试细节：第一个 Agent 被要求给一家宠物店搭网站，代码漏洞百出；第二个 Agent 接到「尝试攻击」的指令后，顺着漏洞入侵，把全部客户数据导出——同一类模型既当施工队又当小偷。
  • 教训一，安全不能靠提示词：在系统提示词里写一万遍「遵守安全规范」，面对带攻击性的指令也形同虚设；提示词是软约束，代码和权限才是硬防线。
  • 教训二，最小权限加沙箱：给 Agent 的每个 API 和数据库连接都设成只读或隔离范围，批量导出、删除、向外发数据这类操作必须停下来等人审批。
  • 教训三，AI 写的代码不能让同一个模型自己审：要过静态代码扫描、自动化测试流水线（CI）和人工复核，才能上线到生产环境。

评论总结

  • 亮点HuntTheEdge 指出写代码的 Agent 和攻击的 Agent 用的是同一种能力；他的做法是只给 Agent 最小权限的密钥、生产数据库默认只读、上线前单独跑一个「红队」Agent 专门找漏洞。
  • 共识jeff20250405 和 0xm0reyu 都认为 AI 写的代码就是你自己的代码，出了事责任在签字上线的人，指望厂商负责是想多了。
  • 分歧Kiki9zpr 觉得这可能是早期版本的问题、新模型早修好了；AYi 回应说模型是按概率生成内容的，不可能有百分之百可靠的提示词约束，推理能力越强、绕过规则的能力也越强，与其等厂商修补，不如在自己的架构上设防。

这条把三位投资人关于 AI 算力的说法放在一起看。a16z 的 Ben Horowitz 回忆了互联网泡沫时期自己创办 Loudcloud 的教训：带宽最贵、最缺的时候签下高价长约，两年后价格崩盘，借钱囤带宽的公司全被拖垮。AYi 把这段历史套到今天：AI 模型的调用价格一直在降，但显卡、机房和电力还在涨价，借钱买卡再出租算力的公司两头受挤，所谓短缺是暂时的。另一位基金经理 Gavin Baker 持反方意见，认为今天的算力是真被用满了，和当年不能类比。这能帮你判断「算力泡沫」类新闻到底在争什么。

核心要点

  • Loudcloud 的数字：1999 年带宽每兆位约 1500 美元、有钱还买不到，他们被迫签了三年长约；仅两年后跌到约 50 美元，但合同还得按原价付。
  • AYi 总结的风险机制叫「刚性负债配浮动收入」：借钱买卡的利息、机房长约的租金是固定的，而出租算力的价格随市场浮动；一旦新芯片或新算法让同样的活需要更少算力，租金下跌，现金流先断。
  • Baker 的反方论据是利用率：2000 年泡沫顶峰时约 97% 的光纤埋在地下没用过，而今天几乎找不到闲置的顶级 GPU，需求是真实的。
  • Horowitz 引用 Databricks CEO Ali Ghodsi 的「快速起飞」四条件：新模型所需 GPU 远少于上一代、训练更快、更准，且这三点不断重复；他认为目前一条都没达到，所以算力需求短期不会突然塌掉。
  • 读新闻时可看三件事：公司背了多少债和长约、算力单价降得多快、用量涨得是否比单价降得快。
