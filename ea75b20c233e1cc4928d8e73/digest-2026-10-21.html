DeepSeek 把支撑 V4.1-Flash 大规模线上服务的自研推理框架 DeepInfer 开源，并同时开源配套组件 deepseek-recipe。模型权重好比一本菜谱，推理框架则是后厨的出餐系统：负责接请求、排队、在显卡上把答案算出来，调度得好，同样的显卡能多服务几倍的用户。DeepSeek 说开源这套生产栈，是为了帮业界省算力、省电、把 AI 用价压下来，以后新模型的推理代码也会放进这个仓库。宝玉的中文解读补充了门槛：它只能跑在英伟达 Blackwell 一代数据中心显卡或华为昇腾 950 上，官方测试用了 4 到 64 块卡，个人电脑跑不动，真正用得上的是想自己部署 DeepSeek 的企业和云厂商。

核心要点

  • 主要提速手段是投机解码：先让一个轻量的草稿模型一次猜出后面最多 5 个 token，大模型一次性核对，猜对的直接收下、猜错的才重算。

  • deepseek-recipe 像前台接单员，把 OpenAI 和 Anthropic 格式的请求翻译成 DeepSeek 能读的输入，再把思考过程和工具调用翻译回去，让自建部署的行为和官方 API 一致。
  • 授权很宽松：DeepInfer 用 Apache 2.0、deepseek-recipe 用 MIT，都允许免费商用和修改；recipe 有 Python 和 Rust 两个版本，支持 V4 和 V4.1。
  • Orange AI 的说法是，用上这套框架后自建推理的回本周期从约 10 个月缩到约 4 个月，这是作者转述的估算，不是 DeepSeek 官方数字。

OpenAI API 支持 12 小时提示缓存，长期运行的 agent 隔几小时回来也按缓存价计费↗

OpenAI 开发者平台宣布，API 的提示词缓存（把重复发送的前缀内容存起来，下次按更便宜的价格计费）现在可以选择保留 12 小时，而不只是默认的 30 分钟。这主要面向一整天都在反复使用同一批系统指令、工具定义和上下文的长期运行 agent：即使两次请求隔了几个小时，也能继续按较便宜的缓存输入价计费。同一个请求里还能混用，比如共享指令缓存 12 小时、新对话内容缓存 30 分钟。OpenAI 说只要一天内反复复用，省下的钱会明显超过 12 小时缓存的额外成本。Codex 负责人 Tibo 在同题帖里补充，Codex 和 Work 的登录用户缓存是永久的，回到几小时前的旧对话也一定能命中缓存。

核心要点

  • 新参数在 Responses API 里叫 prompt_cache_options.ttl，取值 "12h"，按评论引用的官方文档只支持 GPT-5.6 及之后的模型。
  • 评论里多人引用官方文档：12 小时档写入缓存的费用是普通输入的 2.5 倍，30 分钟档是 1.25 倍，读取价格相同。
  • 所以只有同一段前缀在一天里被反复读取好几次时才划算，偶尔用一次的 agent 反而会多花钱。
  • OpenAI 官方举的典型场景是 dots 这类常驻 agent：同一套工具定义和指令一天要被调用很多次，隔几个小时再来也算命中。

推荐原因你一直关心 harness 和评测，这篇把“怎么选裁判模型、怎么定阈值”讲成了一套能照做的流程，文中的提示词可以直接交给编程 agent 跑。

最近出现了一批专门做二分类判断的“决策模型”，比如 TypeSafe 的 Jev、Perplexity Decider、Liquid d1、Cloudflare Clef 和 OpenAI Decisions API，它们比用大模型当裁判更快、更便宜，适合用来给 AI 应用做自动评测（eval）。Hamel Husain 和 Antaripa Saha 用一个租房客服 agent 的 100 条对话记录做测试，让每个模型判断哪条记录里出了错，比如订房失败或没有及时转人工，再和人工标注对比。文章的核心提醒是：很多人直接用接口默认的 0.5 阈值，结果白白丢掉不少效果；正确做法是先定好最低的准确率和召回率要求，再用交叉验证调阈值，最后才比较成本。文中还附了两段可以直接交给编程 agent 执行的调阈值和校准提示词。

核心要点

  • 阈值的坑可以用一个例子说明：如果模型给所有出错记录打 0.40、给正常记录打 0.10，阈值设 0.30 能全部分对，用默认 0.50 却一条错误都抓不到。
  • 作者把精确率和召回率都至少 80% 作为可用门槛，只有 Perplexity、Liquid d1-ultra 和 OpenAI Decisions 达标；调阈值时用分层五折交叉验证，在训练折上选阈值、在留出折上评估。
  • 成本对比上，Perplexity 每 100 次评测约 0.82 美分、F1 为 0.79，OpenAI Decisions F1 达到 0.87 但每 100 次约 3.72 美分，大约贵 4.5 倍。
  • 分数能不能当概率用也要先查校准：Clef Flash 有一组记录平均预测出错概率约 8%，实际却有 60% 出错；用 Platt 缩放校准后多数模型改善，但 OpenAI 的反而略变差。
  • 作者建议每种失败类型单独建一个裁判，先用效果够好的大模型，再试小模型能不能以更低成本追平；不同任务上的排名差异很大，必须用自己的数据测。

DeepMind 论文：自我进化的 agent 适应得越多忘得越多，静态基准测不出来↗

elvis @omarsar032.5万 粉丝10月21日 10:10长帖

赞 36转 0评 14阅 2,709

推荐原因你在给自己的 agent 做长期记忆和自动改提示词，这篇论文说清了这样做会忘掉什么、该怎么测。

elvis 推荐了 Google DeepMind 等机构的一篇论文，研究会「自我进化」的 agent 能不能边学新东西边不忘旧东西。作者用 BIRD、BFCL、ScienceWorld 搭了四组会随时间变化主题、流程或领域的任务流，测试 ReasoningBank、GEPA、Meta-Harness 三种方法；它们都不改模型权重，只改提示词、记忆和技能。结论是自我进化在多数任务流上确实提高了总分，但适应得越多、忘掉的也越多：改写共享提示词的方法会一刀切地影响没见过的任务，记忆检索虽然更局部，却会串用别的领域的经验。作者建议用随时间变化的任务流来评测，因为静态基准会把这两个问题掩盖掉。对给自己的 agent 加长期记忆的人，这是一个直接的提醒。

核心要点

  • 三个方法分属两类：ReasoningBank 把成功和失败的经验存成可检索的记忆，GEPA 和 Meta-Harness 直接改写整段提示词或工作区。
  • 核心发现是适应越多、遗忘越多：改写共享提示词属于全局修改，任务一换方向就会覆盖旧知识、干扰没见过的任务。
  • 记忆检索的更新更局部，但相似问题需要不同做法时会互相冲突，比如在 BFCL 的两组任务里跨组和组内的相似度几乎一样。
  • 作者建议用会漂移的任务流来测 agent，只看静态基准分数会误以为自我进化没有代价。

评论总结

  • 共识@adrianogomes 认为 agent 自己写下的经验一旦是错的就会被反复检索，建议把记忆写入当成代码变更来管：有版本、能追溯是哪次运行写的、可以回滚。
  • 亮点@yusufksadek 指出论文里 BFCL 两组任务的跨组相似度和组内相似度几乎一样（约 0.835 对 0.834），所以任何相似度阈值都救不了 ReasoningBank。
  • 疑问@shuangshuang90 说实际使用中自我改进的 agent 常常反复走同一条死路，因为检索出来的是过时计划，真正难的是让旧记忆失效，并追问论文怎么处理。
  • 亮点@DanielLenton1 觉得最反直觉的是把任务打乱交替出现反而让 GEPA 变差（分块提升 5.8、混合只有 0.9），因为几组规则在有限的提示词长度里互相争抢。

Tw93 回应很多人好奇的问题：他怎么在 Mac 上开发 Windows 软件，以及现在 Windows、桌面和移动端一般用什么技术栈。这是系列的第一篇，介绍各种桌面与移动端开发技术（如原生、WPF、WinUI3、Electron、跨平台框架）的取舍和他自己的思考。宝玉在同题帖里补充了自己的踩坑经历：GPUI（Zed 编辑器团队的 Rust 界面框架）性能好、跨平台，但编译慢、不支持热更新、对 agent 验证界面不友好，所以他换回了 Electron，再把需要高性能的部分用 Rust 编译成 WebAssembly 或后台进程。对正在为跨平台客户端选型、又主要靠 AI 写代码的人，两篇合起来很有参考价值。

核心要点

  • Tw93 提到的选型维度包括性能、包体大小、跨平台成本和团队熟悉度，他计划在后续文章里讲在 Mac 上用虚拟机还是真机调试 Windows 软件。
  • 宝玉列出 GPUI 的五个坑：复杂界面要 fork 修改、无障碍支持弱、Rust 编译吃满 CPU 和磁盘、改一点界面要等几分钟到十几分钟、agent 验证界面慢。
  • 他换回 Electron 的主要理由是对 agent 友好：编译快、能热更新，界面还能直接在 agent 内置浏览器里打开验证。
  • 宝玉的折中方案：界面用 Electron 保证迭代速度，重计算部分用 Rust 编译成 WebAssembly 在浏览器里跑，语音转录和合成作为 Rust 子进程，类似 Codex 的架构。
