开源引擎 Magnitude：把 1800 亿的 Qwen 跑进 64GB 的 M4 Max，速度约 56 token/秒↗

Akshay 🚀 @akshay_pachaar29.3万 粉丝11月25日 20:54教程

赞 1,425转 0评 91阅 13.9万

推荐原因如果你一直觉得「本地跑不了超大模型是因为显存不够」，这篇文章把限制从显存改写到了固态硬盘速度，并给了可下载的引擎。如果你有一块够快的 NVMe 固态硬盘、又想在本地跑此前装不下的开源大模型，先让它在下载前给出速度预估，再决定要不要把现有本地工具接上去。

Akshay Pachaar（@akshay_pachaar）介绍了当天开源的本地推理引擎 Magnitude。过去有一条硬规则：模型权重要是放不进显存或统一内存，就跑不起来，所以 1800 亿参数这一档往往得买一两万美元的工作站。他在视频里用 64GB 内存的 M4 Max，在 OpenCode 里跑 Qwen 3.8 Flash Next（1800 亿参数、2-bit 量化、6.4 万上下文），速度约每秒 56 个 token。之所以可行，是因为这类开源模型是稀疏的混合专家（Mixture-of-Experts，每层有许多小组网络，路由器每个 token 只叫醒其中几个）：1800 亿参数里大约只有 60 亿会参与当前计算，其余约 97% 处于闲置。Magnitude 的办法是「固态硬盘专家流式」：把注意力和最常复用的专家留在显存或统一内存，其余放在 NVMe 固态硬盘上，路由器点到再读。项目是 Apache 2.0 许可，完全本地，支持桌面应用、命令行和 Docker。

核心要点

  • 朴素的硬盘流式往往只能跑到每秒两三个 token，常见原因有四个：缓存把马上还要用的专家挤出去、逐层读盘让显卡和硬盘互相等、推测解码一次验证多个 token 会碰到更多专家、以及长提示词把解码依赖的缓存冲掉。
  • Magnitude 的对应做法是：按复用率给专家排序并把头部留在显存、提前预取后续 token 要用的专家、跨层直接读 NVMe 并绕过系统交换分区，以及在预填充阶段每个冷专家每层只读一次、与显卡计算重叠，避免长提示词冲掉热缓存。
  • 流式过程只读不写固态硬盘，所以不会增加闪存磨损；内存或显存越大，能同时留住的热专家就越多，速度仍然会更好。
  • 第一次启动时它会给硬件画像，在下载前预估每个模型的速度，并按芯片微调内核，几乎不用自己设参数；可跑在苹果芯片、NVIDIA、AMD、Intel 或纯 CPU 上，并能一键接上 Claude Code、Codex、OpenCode 和 Cline，也提供兼容 OpenAI 的接口。

推荐原因官方发布往往只说「能自动审 PR」。这份指南把会自动提交、监视何时会停、以及审批文件怎么写都讲清楚了，适合马上要试的人。先在一个你信任的、无关紧要的分支上跑 /code-review 和 /ship，确认它不会把密钥和规则文件一并提交，再考虑留给它盯正式的合并请求。

Addy Osmani（@addyosmani）代表 Claude 团队写了一份实操指南。所谓 Claude Ship，是接在你打开的 Pull Request（合并请求，把代码补丁提交给主分支前的审查单）后面的三组代理：Code Review 负责多角度审查并分类发评论；PR Steward（测试版）跟进失败的检查、合并冲突和评论，但设计上不会批准或合并；Claude Approvals（测试版）则按仓库里的策略文件决定能不能批，像一份更聪明的 CODEOWNERS。云端自动跑通常要管理员打开，但本地命令 /ship 在最新版 Claude Code 里就能用，普通额度也可以先在自己的合并请求上试。作者把人的角色说得很明确：你仍是流程的架构师，要定义做什么、怎么做、以及达到什么标准才能合并。

核心要点

  • 如果你只做一件事：推送前先跑 /code-review 审查当前分支和未提交改动。力度从 low 到 max，low 只报它最有把握的问题；ultra 在云端跑，需要登录 claude.ai，且可能单独计费。
  • /ship 若还没有合并请求，会像执行 git add -A 一样提交待改文件（遵守 .gitignore），必要时建分支，并用当前对话写提交说明，提交前可按 Esc 取消；它不会提交看起来像密钥的文件，也不会提交 CLAUDE.md、REVIEW.md 以及 .claude/、.github/ 里的规则文件，公开仓库则完全不会代你提交。
  • 监视最长约七天，用的是你本机的配额，合上笔记本就会停；Windows 上能打开审查，但监视起不来。不要在 bypass-permissions 模式下监视。只对「你信任能向主分支合并的人」的仓库开监视，因为它必要时会把主分支合进你的分支并跑测试，等于让那些人有机会在你的机器上执行命令。
  • 已有合并请求只想跟进、不必再审一遍时，可在检出该分支后用 /steward；不要把它和管理员启用的团队服务 PR Steward（以 claude[bot] 身份跑）搞混。同一会话同时只能监视一个，可用 /ship stop 或 /steward stop 停掉。
  • 团队策略写在默认分支的 .claude/approvals.yml。建议先用观察模式（observe）记日志、对照真实审查，再改成强制；Claude 的批准在 GitHub 上算真正的批准，若规则只需要一人批准，它自己就可能够。启用计费审查前要先告知预算负责人。

评论总结

  • 亮点tweekdev 提醒第一次用 /ship 就要知道：监视自动提交时会用 git -c core.hooksPath=/dev/null，本地的 Husky 提交前检查不会跑到这些提交上，真正要紧的检查必须放到持续集成里。
  • 亮点SeanLiu7777777 认为没有先写好「哪些路径和操作不能碰」的约束文件，自动批准合并请求就是在抽奖；应先把规则放进仓库，再谈自动化。
  • 疑问waitingforASI_ 问「每个问题最多推 3 次」的上限，是只约束本地监视，还是以 claude[bot] 跑的 PR Steward 也会在 3 次后停手。
  • 分歧CatKingAC 说自己管工程师多年，从来没真正让团队按写下来的策略文件执行，因此对「代理按策略文件批准合并请求」能否落地持保留态度。

核心要点

  • Messages API 是外部应用调用 Claude 时最常用的接口之一，迁移发生在这一层，意味着他们愿意在不中断对外契约的前提下换掉实现语言。

推荐原因如果你已经在多台机器上跑助手，却苦于工具和本地大模型没法安全共享，可以先看这个被比作「AI 界 Tailscale」的项目。若你已经有两台以上机器在跑 Agent，打开项目说明，看它能不能把本地大模型和云上的助手连进同一张加密网。

AI 资讯账号 aigclink（@aigclink）介绍谷歌开源的底层项目 Agent Mesh。作者把它理解成专门给 Agent 用的加密私有网络，并类比为 AI 界的 Tailscale（一种给设备组加密虚拟局域网的工具）。典型场景是：有的 Agent 跑在个人电脑，有的在云服务器，有的在公司内网，还有一台带显卡的工作站专门跑本地大模型——它们不在同一网络里，却需要共享工具和模型。Agent Mesh 的目标就是让这些分布在不同设备和网络中的 Agent 安全连接起来，而不必把全部服务暴露到公网。

核心要点

  • 它解决的是组网和访问控制，不是再做一个新的聊天模型；先搞清「谁可以连谁、共享哪些工具和模型」，再谈智能本身。
